# ADR-018 — Module resolution is project-relative, not same-directory-only

## Status
Accepted

## Context
`ADR-006` restricted `⟲` resolution to same-directory `<name>.obk` files, deliberately: "module search paths beyond the entry directory... rejected... as coupled to the still-unresolved artifact/distribution model, which this decision deliberately does not presuppose." `ADR-017` now defines that model (a Project rooted at a discovered marker). This ADR is the follow-through `ADR-006` reserved: deciding how an import name maps to a file once the search space is a Project, not a single directory.

## Decision
`ImportDeclaration`'s `ModuleName` stays exactly what `ABSTRACT_GRAMMAR.md`/`CONCRETE_SYMBOLIC_GRAMMAR.md` already define — a single `Ident`, no new separator syntax. This is deliberate, not an oversight discovered late: a compound, slash-separated import name (`⟲ utils/strings`) would require the lexer to tokenize `/` within `ModuleName`, which is a real surface-syntax change, contradicting this ADR's own premise that import syntax doesn't change. What generalizes is entirely resolution, not spelling: given a bare name, the resolver searches every `.obk` file reachable under the Project root (or, in bare-file mode with no marker, just that lone file's own directory — collapsing to `ADR-006`'s original same-directory behavior unchanged) for one whose filename (minus `.obk`) matches the imported name. Exactly one match resolves normally. Two or more matches (the same base name present in different subdirectories of one Project) is a static error, in the same family as `ADR-006`'s "already bound" collision — an ambiguous name, not silently resolved by first-found order. Path/root containment reuses the same lexical logic `ADR-019` defines for filesystem access — one boundary mechanism, not two independently-maintained ones. `ADR-006`'s other decisions (whole-module-only imports, no selective/aliased syntax, "already bound" collision handling for same-name bindings) are unchanged and are not reopened by this ADR.

Importing another Project (a directory tree with its own, separate marker) is explicitly out of scope: nothing in this model gives an external Project an identity to resolve by (name? version? location?), and inventing one is a separate, later decision — this ADR only generalizes resolution *within* one Project's own tree.

**Stated explicitly, because it is a real, load-bearing consequence and not an incidental detail:** a module's identity is its filename alone — `src/strings.obk` and `vendor/strings.obk` are the same name (`strings`) from the resolver's point of view, and both existing in one Project makes `⟲ strings` ambiguous, not "same name, different scope." Directory structure inside a Project is not part of a module's addressable identity; it organizes files on disk and nothing more. This is a direct consequence of keeping `ModuleName` a single `Ident` (above) rather than a compound path, not a separate policy choice layered on top of it — a resolver could not honor directory-qualified identity without also accepting directory-shaped import syntax, which this ADR already rejected.

## Alternatives Considered
Keeping same-directory-only resolution and layering a separate "project mode" resolver on top was rejected: it would mean two import-resolution algorithms to maintain and reason about, when whole-tree search already subsumes same-directory as its degenerate (single-directory) case. Allowing imports to reach outside the Project root (e.g. `../sibling-project/foo`) was rejected as directly contradicting the filesystem boundary `ADR-019` establishes — an import that could escape the root would make that boundary meaningless. A compound, slash-separated import name mirroring the resolved path exactly (`⟲ utils/strings`) was considered and rejected for this decision specifically because it requires a `ModuleName` grammar change — out of proportion for a CLI-side resolution question, and avoidable entirely by resolving on basename uniqueness instead.

## Consequences
`crates/obfusku-cli/src/modules.rs`'s resolver must change its path-construction rule from `base_dir.join("{name}.obk")` (same-directory-only) to a whole-Project-tree search by basename, with an explicit ambiguity error when more than one candidate matches. Module identity (currently the canonicalized absolute path) should become root-relative, so the same module is recognized as the same module regardless of where the Project happens to sit on disk. `ADR-006`'s status remains Accepted; this ADR supersedes only the "no search paths beyond the entry directory" clause of its Consequences, not the rest of that decision.
