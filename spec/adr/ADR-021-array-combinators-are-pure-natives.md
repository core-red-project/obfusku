# ADR-021 — `Array<T>` combinators are host-provided natives despite being pure, extending the native mechanism beyond the I/O boundary it was scoped to

## Status
Accepted

## Context
`ADR-010` established natives as the mechanism for capabilities the runtime cannot express in Core — scoped, in its own wording, to "I/O is host-provided." `List<T>`'s combinators (`⟐`/`⌿`/`⌽`) needed no such mechanism: they are ordinary `.obk` source, written by recursion against `Cons`/`Nil` pattern matching, loaded through the same `stdlib::load` path as any user module. `Array<T>`'s combinators (`GLYPH_SYSTEM_DESIGN.md` §10.5: `⊡`/`⊟`/`⊞`/`#`/`⊙`) cannot be written the same way — `SEMANTIC_CORE.md` §9.1 deliberately excludes `Array` from structural pattern matching (open head/rest destructuring), which is exactly the mechanism `List`'s combinators are built from. There is no way to write a loop or structural recursion over an `Array` in Obfusku surface syntax at all; the only operations the language gives a program over an `Array` are literal construction and `IndexExpr` (`arr[i]`).

## Decision
`Array`'s five combinators are host-provided natives, registered the same way `natives.rs`'s I/O natives are (a hand-authored `Scheme` seeded into the ambient prelude, implemented as a Rust closure), despite doing no I/O and having no observable effect — they are pure functions over `Value::Array`. `ADR-010`'s native mechanism is hereby understood to cover any capability the language cannot express in its own surface syntax, not only ones that cross the host boundary; I/O was its first instance, not its defining property. `ADR-010`'s other decisions (arity-1/curried natives, shared tagged-failure mechanism, host-authored type schemes independently tested against their implementation) apply to these natives unchanged — a purity difference doesn't warrant a second registration mechanism.

**`obfusku_runtime::eval::apply_value` — scoped narrowly, stated explicitly so it is never mistaken for more than it is.** `map`/`filter`/`fold` each need to invoke a caller-supplied Obfusku function from Rust, which no prior native ever needed (I/O natives are leaf calls, never call back into user code) — `apply_value` is the one piece of new runtime surface this decision requires, and its scope is exactly:

1. **Host-native → Obfusku-callback infrastructure, nothing broader.** It exists so a native can invoke one already-evaluated `Value` (a `Closure` or `Native`) against one already-evaluated argument — the same dispatch `Expr::Apply` already performs, factored out. It is not a general "run this Obfusku code" entry point, and has no path from arbitrary Rust code to constructing or evaluating a `Core::Expr` from scratch.
2. **Introduced by, and scoped to, `Array`'s combinators.** It has no callers outside `array_native.rs` as of this decision; nothing about this ADR licenses using it as a general-purpose escape hatch for some future native that merely finds it convenient.
3. **Not a new language primitive.** Nothing changes in `SEMANTIC_CORE.md`, `ABSTRACT_GRAMMAR.md`, or `CONCRETE_SYMBOLIC_GRAMMAR.md` — `apply_value` is Rust-side plumbing inside the host, invisible to and unreachable from Obfusku surface syntax itself.
4. **Does not change the evaluator's TCO guarantee.** `SEMANTIC_CORE.md` §14.1's tail-call guarantee is about `eval`'s own trampoline loop for Obfusku-to-Obfusku calls; `apply_value` is deliberately *not* trampolined (documented on the function itself) — each call it makes is one bounded, non-tail Rust stack frame, exactly like any other native's call into `(f.func)(av)` already was. A combinator built on it is bounded by the target `Array`'s length times one Rust frame per element, never by unbounded user-controlled recursion depth the way a `List`-recursive function's own tail calls are.
5. **Exposes no additional capability.** It cannot reach the filesystem, cannot be handed anything other than values already reachable through ordinary evaluation, and does not widen what a native can observe or do beyond "call a function value with an argument value" — the same operation `Expr::Apply` already performs, now reachable from native Rust code too.

## Alternatives Considered
Adding a general-purpose looping or explicit-recursion primitive to the Core, so `Array` combinators could be written in `.obk` like `List`'s, was rejected as a disproportionate Core-language change to avoid five native function bodies — `DESIGN_VISION.md` §10 already settled "no general loop construct exists in the Core... combinators over built-in collections... is the design, not a placeholder," and this would reopen that. Treating `Array` combinators as somehow not "real" natives (a lighter-weight registration path, skipping the Scheme/implementation-agreement testing discipline `ADR-010` requires) was rejected: nothing about purity reduces the risk of a hand-written `Scheme` disagreeing with its Rust body — the same testing obligation applies.

## Consequences
`crates/obfusku-cli/src/natives.rs` (or a sibling module under the same crate) gains five new native registrations with no filesystem/I/O capability threaded through them — unlike `readFile`/`writeFile`, they need no `base_dir` and are available unconditionally, including in the REPL (`ReplSession`), the same way `print`/`readLine` already are via `load_io_only`. Any future capability the language cannot express in surface syntax (a hypothetical future collection type's own combinators, for instance) should default to this same native pattern rather than reopening whether "native" implies "I/O."
